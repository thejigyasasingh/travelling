# 3. UUIDv7 primary keys

**Status:** Accepted · **Date:** 2026-08-06

## Context

Primary keys here are generated by the application, not the database: an
aggregate has an identity before it is persisted, use cases return ids, and the
outbox event referencing a booking is written in the same transaction that
creates it.

That rules out `bigserial`. The remaining question is which UUID.

`uuid4` is random, and random primary keys are a real cost on a table with
millions of rows. B-tree inserts land at random leaves, so the index working
set is the whole index rather than its tail; page splits are frequent; and
`ORDER BY created_at` cannot use the primary key at all.

## Decision

**UUIDv7**, via `uuid-utils`.

The first 48 bits are a Unix millisecond timestamp, so values generated in
sequence sort in order. Inserts append to the right-hand edge of the index the
way a sequence does, while the id stays globally unique and safe to generate in
the application, in a worker, or on a phone that is offline.

## Consequences

**Good.** Index locality of a sequence with the independence of a UUID. Ids sort
chronologically, which makes keyset pagination on `(created_at, id)` a
tie-break rather than a second column. No round trip to reserve an id.

**Bad.** The creation time is embedded and therefore public. A booking
reference exposed in a URL leaks roughly when it was made. Acceptable here —
and the reason guest-facing references are a separate `RW-YY-XXXXXXXX` column
rather than the id.

**Bad.** 16 bytes rather than 8, and a dependency for generation. Postgres has
no native v7 generator until 18, so `gen_random_uuid()` in a migration is v4 —
which is fine for a backfill and wrong for a hot table.

## What would change this

Postgres 18's native `uuidv7()` removes the dependency for database-side
generation. It does not change the choice, only where it can be made.
